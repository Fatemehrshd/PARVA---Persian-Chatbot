# طراحی: سهمیه دوره‌ای کاربران (ریست ساعتی) + نرخ‌گذاری بر اساس نوع کار

تاریخ: 2026-09-18 — وضعیت: در انتظار تایید

## ۱. هدف

1. ادمین بتواند به ازای **نوع کار مدل** (پاسخ عادی، تصویر، سند، تفکر عمیق) نرخ دلاری متفاوت به ازای هر ۱۰۰۰ توکن تعیین کند.
2. سهمیه مصرف (توکن و تعداد پیام) **دوره‌ای** شود: پس از پایان هر دوره ساعتی، شمارنده‌ها ریست می‌شوند.
3. با اتمام سهمیه (توکن یا پیام)، ارسال پیام کاملاً مسدود و در UI چت به صورت واضح اعلام شود.

## ۲. تصمیم‌های قفل‌شده (تایید کاربر)

- سقف اختصاصی کاربر هم از **شمارنده دوره** می‌خواند (نه مادام‌العمر).
- سقف تعداد پیام در هر دو سطح **نقش و کاربر** است.
- واحد دوره ریست **ساعت** است؛ **پیش‌فرض ۶ ساعت**. `0/null` = بدون ریست (رفتار مادام‌العمر فعلی).
- ریست دوره **تنبل** است (بدون cron): هنگام اولین چک/ارسال بعد از پایان دوره.
- `usedTokens` مادام‌العمر برای آمار داشبورد دست‌نخورده می‌ماند؛ سقف‌ها فقط از شمارنده دوره می‌خوانند.
- ورودی ادمین برای نرخ نوع کار **فقط ضریب** است (چند برابرِ پیام عادی)؛ نرخ دلاری و پیش‌نمایش هزینه خودکار محاسبه می‌شود. توکن معادل عکس توسط بک‌اند از ابعاد فایل تخمین زده می‌شود.

## ۳. بخش A — ضریب هزینه به ازای نوع کار

### مدل ورودی (تصمیم کاربر)
ادمین **فقط ضریب** را وارد می‌کند (چند برابرِ پیام عادی)؛ نرخ دلاری هر نوع = ضریب × نرخ عادی (`tokenRatePer1000`). ادمین هیچ نرخ دلاری خام یا تخمین توکن وارد نمی‌کند.

### داده
- کلید جدید `task_multipliers` در `system_settings`:
  ```json
  { "image": 2.5, "thinking": 3, "document": 1.5 }
  ```
  کلید غایب = ضریب ۱ (مثل عادی). `normal` خودِ مبناست و ضریب ندارد.
- نرخ مؤثر هر نوع: `effectiveRate(t) = tokenRatePer1000 × multipliers[t] ?? 1`
- ستون جدید روی `users`: `usageByType` (jsonb) — شمارش توکن به تفکیک سطل: `{ normal: 1200, image: 800, ... }`.

### توکن معادل عکس (سیستم‌محور — ادمین تخمین نمی‌زند)
توکن پیام تصویری از ابعاد فایل تخمین زده می‌شود (فرمول مشابه Anthropic): `(عرض × ارتفاع) / 750`، حداقل ۱ توکن. سند = توکن متن استخراج‌شده (طبیعی است). تفکر عمیق = توکن reasoning (وقتی فاز ۲ آمد).

### تشخیص نوع کار هر پیام (در ChatService)
| شرط | نوع |
|---|---|
| پیام دارای فایل تصویر | `image` |
| پیام دارای سند (pdf/excel/text) | `document` |
| تفکر عمیق فعال (فاز ۲ — آینده) | `thinking` |
| بقیه | `normal` |

### محاسبه هزینه
`usedCostUsd = Σ (usageByType[t] × tokenRatePer1000 × (multipliers[t] ?? 1)) / 1000`
— در لحظه محاسبه می‌شود؛ تغییر ضریب یا نرخ عادی، هزینه گذشته را هم به‌روز محاسبه می‌کند. `GET /admin/users` فیلد محاسبه‌شده `usedCostUsd` را برمی‌گرداند و ستون «مصرفی» جدول کاربران از آن می‌خواند.

### UI پنل ادمین
کارت «ضریب هزینه بر اساس نوع کار» در بخش System Policies — جدول:

| نوع کار | ضریب (ورودی ادمین) | نرخ مؤثر دلاری (خودکار) | هر پیام متوسط ≈ (خودکار) | ویرایش |
|---|---|---|---|---|
| پاسخ عادی | — (مبنا ×۱) | $10 | $0.005 | — |
| کار با تصویر | ×۲.۵ | $25 | $0.012 | ✏️ |
| کار با سند | ×۱.۵ | $15 | $0.007 | ✏️ |
| تفکر عمیق | ×۳ | $30 | $0.015 | ✏️ |

- «هر پیام متوسط ≈» = میانگین توکن پیام عادی کاربران (از داده واقعی، محاسبه آماری ساده) × نرخ مؤثر آن نوع — برای شهود ادمین.
- فیلد موجود «نرخ هر ۱۰۰۰ توکن به دلار» به عنوان «نرخ عادی (مبنا)» داخل همین کارت ادغام می‌شود (حذف تکرار از کارت بالا).
- مودال ویرایش هر نوع: فقط فیلد ضریب (عدد مثبت، مثلاً 2.5)، همان الگوی `RoleTokenLimitModal`.

## ۴. بخش B — سهمیه دوره‌ای به ازای نقش و کاربر

### داده
- ارتقای `role_token_limits` به کلید جدید `role_quotas` با مهاجرت تنبل (اگر `role_quotas` نبود، از `role_token_limits` seed می‌شود):
  ```json
  { "user": { "tokenLimit": 50000, "messageLimit": 100, "resetHours": 6 } }
  ```
- ستون‌های جدید `users` (+ migration):
  - `periodStart` (timestamptz, nullable)
  - `periodUsedTokens` (int, default 0)
  - `periodUsedMessages` (int, default 0)
  - `messageLimit` (int, nullable) — سقف پیام اختصاصی کاربر

### اولویت‌ها (resolve در سرور)
- `tokenLimit مؤثر = user.tokenLimit ?? role.tokenLimit ?? globalTokenLimit`
- `messageLimit مؤثر = user.messageLimit ?? role.messageLimit ?? null` (null = نامحدود)
- `resetHours = role.resetHours ?? 6`

### منطق ریست تنبل (در ابتدای هر generate و هر GET quota)
اگر `resetHours > 0` و (`periodStart` خالی باشد یا قدیمی‌تر از `resetHours` ساعت) →
اگر خالی: فقط `periodStart = now` (شروع دوره در اولین مصرف).
اگر قدیمی: `periodUsedTokens = 0`, `periodUsedMessages = 0`, `periodStart = now`.

### قواعد مسدودسازی (ChatService.generate)
```
blocked توکن   = tokenLimit > 0 && periodUsedTokens >= tokenLimit
blocked پیام   = messageLimit > 0 && periodUsedMessages >= messageLimit
اگر هرکدام → خطای ساختاریافته QuotaExceededException (کد: QUOTA_EXCEEDED)
```
پس از عبور از چک: `periodUsedMessages += 1` و پس از پاسخ: توکن‌ها به `usedTokens` (مادام‌العمر)، `periodUsedTokens` و `usageByType[taskType]` اضافه می‌شوند.

### اندپوینت وضعیت سهمیه
`GET /chat/quota` →
```json
{ "blocked": true, "reason": "messages|tokens", "remainingTokens": 1200,
  "remainingMessages": 0, "resetAt": "2026-09-18T21:30:00Z" }
```

### UI چت (مسدودسازی)
- چت‌استور بعد از mount و بعد از پایان هر استریم `GET /chat/quota` را می‌گیرد.
- وقتی `blocked`: کامپوزر و دکمه «گفتگوی جدید» غیرفعال + بنر بالای کامپوزر:
  «تا ساعت HH:mm امکان ارسال پیام ندارید.» (HH:mm با `resetAt` و فرمت فارسی/ایران — util موجود `IranDate`).

## ۵. UI جدول نقش‌ها (بعد از این فیچر)

| نقش | سقف توکن | حداکثر پیام | دوره ریست | ویرایش |
|---|---|---|---|---|
| کاربر عادی | ۵۰٬۰۰۰ | ۱۰۰ | هر ۶ ساعت | ✏️ |

- مودال `RoleTokenLimitModal` سه فیلد: سقف توکن (دلار↔توکن)، حداکثر پیام، دوره ریست (ساعت، پیش‌فرض ۶، 0=بدون ریست).

## ۵.۵. بخش C — نمایش درصد باقی‌مانده در منوی پروفایل + Interceptor

### منوی پروفایل (`ProfileMenu.vue`)
- با کلیک روی نام کاربر پایین سایدبار، بالای منو یک آیتم **غیرقابل کلیک** (display-only) اضافه می‌شود:
  `۸۴٪ باقی‌مانده` با همان رنگ‌بندی جدول ادمین (>۵۰٪ سبز، ۲۰-۵۰٪ نارنجی، <۲۰٪ قرمز، نامحدود = ∞ سبز).
- منبع داده: همان `GET /chat/quota` (یا snapshot پیوسته به `/me`).

### Interceptor دوطرفه (همگام‌سازی پنل ادمین و سشن کاربر)
- **بک‌اند — `QuotaInterceptor` (NestJS):** روی مسیرهای احرازشده (chat, profile, conversations) snapshot سهمیه کاربر را به پاسخ می‌چسباند (هدر `X-User-Quota` base64/JSON یا فیلد `_quota` در envelope) — هر پاسخی که کاربر می‌گیرد، وضعیت سهمیه‌اش تازه است.
- **فرانت — interceptor در لایه `request` موجود:** بعد از هر پاسخ، `_quota`/هدر را می‌خواند و store مشترک سهمیه (Pinia، مثلاً داخل `authStore` یا `useQuotaStore`) را به‌روز می‌کند. `ProfileMenu` و کامپوزر چت هر دو از همین store می‌خوانند — پس با هر تعاملی (ارسال پیام، باز شدن صفحه، هر fetch) درصد تازه می‌شود.
- **optimistic سمت ادمین:** ذخیره سقف نقش/کاربر در پنل، سقف مؤثر را بلافاصله در جدول کاربران آپدیت می‌کند (بدون refetch) و در صورت خطا rollback (الگوی `AdminModelsSection.setPlatformDefault`).
- **معنای «همزمان» بین سشن‌ها (صادقانه):** سشن ادمین و سشن کاربر دو مرورگر جدا هستند؛ آپدیت آنیِ cross-session یعنی پوش SSE. در این نسخه: سشن کاربر با **اولین پاسخ بعد از تغییر ادمین** تازه می‌شود (interceptor) — در عمل چون چت مدام درخواست دارد، تأخیر محسوس نیست. اگر پوش لحظه‌ای لازم شد، در نسخه بعد از روی کانال SSE موجود اضافه می‌شود (خارج از محدوده این نسخه).

## ۶. تست‌ها

- بک‌اند: ریست تنبل (عبور از دوره)، بلاک با توکن، بلاک با پیام (توکن باقی‌مانده)، اولویت کاربر>نقش>سراسری برای هر دو بعد، محاسبه هزینه با ضریب تفکیکی + تغییر ضریب/نرخ، seed مهاجرت `role_token_limits`→`role_quotas`، چسبیدن snapshot سهمیه توسط `QuotaInterceptor`.
- فرانت: مودال نقش‌ها (سه فیلد)، مسدودسازی کامپوزر + بنر ساعت ریست، جدول ضرایب، آیتم غیرقابل کلیک درصد باقی‌مانده در `ProfileMenu` با رنگ‌بندی درست، به‌روزرسانی store توسط interceptor.

## ۷. بخش D — مدیریت دسترسی مدل‌ها (فاز ۲، بعد از سهمیه‌ها)

### تصمیم‌های قفل‌شده (تایید کاربر)
- گروه کاربری = همان `role` (entity جداگانه «گروه» ساخته نمی‌شود).
- مدل «اختصاصی» با وایت‌لیست کاربران روی خود مدل (نه سطح نقش).

### داده
- فیلد جدید روی `AiModel`: `accessLevel: 'public' | 'commercial' | 'private'` (default `'public'`) + migration.
- فیلد جدید روی `AiModel`: `allowedUserIds` (jsonb آرایه‌ای از userId) — فقط برای سطح `private` استفاده می‌شود.
- کلید جدید در `system_settings` یا ستونی در `role_quotas`: `modelAccess` به ازای هر نقش — آرایه سطوح مجاز:
  ```json
  { "user": ["public"], "manager": ["public", "commercial"], "admin": ["public", "commercial", "private"] }
  ```
  (نقش admin همیشه همه سطوح را دارد.)

### قاعده دید (resolve در سرور — تابع خالص قابل تست)
```
مدل غیرفعال (isActive=false)   → مخفی
accessLevel = public            → برای همه‌ی کاربران فعال
accessLevel = commercial        → اگر modelAccess[role] شامل 'commercial' باشد
accessLevel = private           → اگر userId در allowedUserIds مدل باشد
```

### نقاط اعمال (هر سه الزامی)
1. **`GET /models`** — فقط مدل‌های مجاز کاربر جاری در پاسخ باشد (بر اساس JWT).
2. **`ChatService.generate`** — اعتبارسنجی سمت سرور: `modelId` پیام باید برای کاربر مجاز باشد؛ وگرنه خطای ساختاریافته (فارسی: «به این مدل دسترسی ندارید»).
3. **مدل پیش‌فرض (ستاره/`GET /models/default`)** — اگر پیش‌فرض پلتفرم برای کاربر مجاز نبود، اولین مدل مجاز (به همان ترتیب لیست) به عنوان پیش‌فرض مؤثر برگردد.

### UI پنل ادمین
- **`ModelEditorModal`** (موجود): select «سطح دسترسی» (عمومی/تجاری/اختصاصی)؛ با انتخاب «اختصاصی»، انتخاب‌گر کاربران (جستجوی ایمیل، چندتایی) نمایش داده می‌شود.
- **مودال ویرایش نقش** (بخش ۵): چک‌باکس «دسترسی به مدل‌های تجاری» — تنظیم نقش است نه مدل.

### تست‌ها
- فیلتر `GET /models` بر اساس سطح/نقش/وایت‌لیست؛ بلاک `generate` با modelId غیرمجاز؛ fallback پیش‌فرض؛ دسترسی admin به همه.

## ۸. خارج از محدوده این نسخه

- ریست خودکار زمان‌بندی‌شده (cron) — ریست تنبل کافی است.
- نرخ به ازای مدل خاص (فقط نوع کار).
- اشتراک/پلن مدت‌دار با جدول plans.
- entity جدید «گروه کاربری» — نقش‌ها جایگزین آن هستند.
- پوش لحظه‌ای cross-session سهمیه (SSE) — نسخه بعد در صورت نیاز.
